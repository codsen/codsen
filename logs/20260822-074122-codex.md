# CI/CD cold-path optimisation review

This review revalidates `logs/20260817-claude.md` against the current GitHub
Actions workflows, shared actions, Turbo task graph, and public hosted-run
metadata. The August plan has already delivered a large warm-cache win: two
current runs completed end to end in under four minutes. The remaining problem
is the cold and broadly invalidated path, which still takes roughly 12 minutes.

## Conclusion

The August work was directionally correct and mostly implemented. The largest
duplicate gate was removed, cacheable definitions were added, the installed
tree and Turbo cache are now restored, PR CI uses shallow clones, Turbo uses
runner-sized concurrency, and workflow linting moved off the critical path.
Those changes reduced a cache-hit run from the reported 15-minute baseline to
about four minutes.

The sub-five-minute target is therefore met only when the cache remains usable.
It is not met for lockfile changes, release-version changes, or changes inside
the root workspace's large internal dependency closure. Three recent cold or
broadly invalidated runs took 11m45s, 12m03s, and 12m50s. In each, the shared
verification action consumed 8m49s to 9m25s; the longest downstream job added
only about two minutes. Optimising the Node matrix first would attack the wrong
side of the dependency boundary.

The first implementation batch should therefore be REV-001 through REV-005:
make the opaque validation step measurable, narrow cache invalidation, remove
the root-global internal dependency closure, reduce TypeScript startup, and
batch compatibility packing. Only then should job-level parallelism be judged.

There are no P0 or P1 findings. None of the proposed runtime work justifies
weakening coverage, dropping a supported Node lane, removing Chromium 58
validation, trusting cached publish artifacts, or bypassing npm-production
approval.

## How to use this plan

1. Complete REV-001 first and preserve the same measurements for every later
   change.
2. Take REV-002 and REV-003 before redesigning TypeScript or the job graph;
   otherwise improvements will be hidden behind unnecessary global cache
   misses.
3. Implement and measure REV-004 and REV-005 independently so their effects are
   attributable.
4. Attempt REV-006 only if coverage remains material after inner-gate telemetry
   exists.
5. Reassess REV-007 after the P2 work. Do not add runner fan-out merely because
   the current composite action is serial.
6. Update each item's status, resolution, and validation results without
   deleting its original evidence.
7. Compare both a deliberate cold run and a warm affected-package run. A warm
   result alone does not satisfy the sub-five-minute objective.

## Repository guardrails

- Preserve the Chromium 58 artifact gate and Windows CLI/build smoke. These test

## P2 — Fix the cold and broadly invalidated path

### REV-001 — Expose inner-gate, cache-hit, and critical-path timings

- Status: Pending
- Evidence status: Verified observability gap
- Evidence:
  - `.github/actions/verify-repository/action.yml:37-211` contains more than 20
    inner steps, but the public jobs API reports them as one `Verify the
    repository` step lasting anywhere from 44s to 9m25s.
  - The August audit had to use local timing and explicitly identified missing
    hosted step evidence as its largest caveat.
  - The current hosted data can distinguish validation, packing, and downstream
    jobs, but cannot attribute the cold validation time among build, typecheck,
    coverage, examples, and generated-data checks.
- Problem: The next optimisation cannot be ranked or regression-tested reliably
  while 8-9 minutes of cold work is represented by one number. Cache misses and
  genuine command slowdowns are also indistinguishable in the durable run
  summary.
- Recommended change:
  - Add a shared timing wrapper or equivalent instrumentation that records each
    gate's wall time and status in machine-readable JSON and a concise
    `$GITHUB_STEP_SUMMARY` table.
  - Capture Turbo task totals, cache hits, cache misses, and the run summary for
    build, typecheck, examples, `lect:check`, and coverage.
  - Record the workflow's critical path separately from aggregate runner time.
  - Keep command output and failure propagation unchanged, and never copy
    secrets or full environment data into an artifact.
- Done when:
  - A maintainer can compare cold, warm, package-only, lockfile-changing, and
    release runs without downloading raw logs.
  - The summary identifies which gate and which cache class caused a run to
    exceed five minutes.
- Validation:
  - Run one deliberate cache hit and one deliberate cache miss.
  - Force one instrumented command to fail in a test fixture and confirm the
    original exit status and useful output survive.

### REV-002 — Preserve unaffected task entries across lockfile changes

- Status: Pending
- Evidence status: Verified configuration; exact Turbo 2.10.8 mutation matrix
  still required before editing
- Evidence:
  - `turbo.json:20-21`, `:79-80`, `:98-99`, and `:345-346` explicitly include
    the root lockfile or root manifest in package task inputs.
  - `.github/actions/verify-repository/action.yml:61-66` keys both the installed
    tree and Turbo cache on the complete lockfile hash.
  - `.github/actions/verify-repository/action.yml:105-115` refuses to restore a
    Turbo cache produced under any earlier lockfile.
  - Turborepo already models lockfile changes in its global and package hashes;
    its current documentation distinguishes root dependency changes from
    lockfile changes affecting one package.
  - `ops/helpers/tests/turboInputs.test.js` validates source, test, and generated
    input selectivity but does not mutate a workspace dependency or lockfile.
- Problem: A package-local dependency update discards cached work for all 112
  workspaces twice: the Actions cache cannot retrieve the earlier content, and
  explicit task inputs make the complete lockfile part of each task hash. The
  August audit called this an accepted ceiling, but current Turbo has enough
  dependency information to test and narrow it safely.
- Recommended change:
  - Extend the Turbo input fixture to cover unrelated package dependency bumps,
    dependency-closure bumps, root toolchain bumps, and lockfile-only changes
    under the repository's installed Turbo version.
  - Remove explicit root lockfile inputs wherever Turbo's package graph already
    supplies the correct dependency-scoped invalidation. Retain explicit files
    only where the command reads their contents independently of package
    resolution.
  - Give the Turbo Actions cache a format/version and OS prefix that can restore
    content-addressed entries across lockfile revisions. Keep the
    `node_modules` cache exact-lockfile keyed.
  - Add bounded cache pruning before save if cross-lock retention materially
    increases upload size; use measured access behavior rather than wiping the
    cache.
- Prerequisites: REV-001
- Done when:
  - Updating one package's external dependency invalidates that package and its
    real dependents, not all workspaces.
  - Updating root TypeScript, esbuild, c8, or another genuine shared tool still
    invalidates every task whose result can change.
  - A lockfile-changing hosted run restores prior unaffected task entries and
    reports those hits.
- Validation:
  - Extend `ops/helpers/tests/turboInputs.test.js` with controlled before/after
    hash assertions.
  - Compare `turbo run ... --dry=json` and `--summarize` output for each mutation
    class.
  - Run the complete shared verifier once cold and once from the resulting
    cross-lock cache.

### REV-003 — Remove the 46-package root-global source closure

- Status: Pending
- Evidence status: Verified against the current Turbo package graph
- Evidence:
  - Root `package.json` declares nine published workspaces in
    `devDependencies`; Turbo currently resolves seven of them as direct internal
    dependencies of its `//` pseudo-package.
  - Those seven dependencies expand to a 46-package transitive workspace
    closure in `turbo query`.
  - The current Turbo dry run reports a non-empty
    `globalCacheInputs.hashOfInternalDependencies`.
  - Turborepo documents that source files in internal packages used directly or
    transitively by the root workspace enter the global hash and cannot be
    excluded through ordinary task inputs.
  - Some root entries are genuine tooling inputs, such as `detergent` and
    `json-comb-core` in `ops/scripts/generate-info.js:188-189`; others have no
    live root import outside generated or historical text and need a usage
    audit.
- Problem: A source edit anywhere in this 46-package closure makes every
  cacheable task miss, even when the edited package is unrelated to most
  workspaces. CI 62 changed `codsen-utils`, which is a direct root dependency,
  and then paid the cold validation path.
- Recommended change:
  - Remove stale root workspace dependencies.
  - Move genuine root-tool dependencies behind an explicit infrastructure
    boundary, or load already-built workspace artifacts by explicit path after
    declaring their build ordering. Do not replace current-package tooling with
    stale registry copies merely to improve a hash.
  - Keep `lect`, generated-data, changelog, and release dependencies visible in
    Turbo task relationships and inputs so cache correctness does not depend on
    npm hoisting.
  - If a private infrastructure workspace is introduced, extend the
    authoritative package-kind model rather than creating an undeclared
    workspace exception.
- Prerequisites: REV-001
- Done when:
  - The root pseudo-package has no avoidable internal workspace dependencies.
  - Changing `codsen-utils` or another former root-closure package invalidates
    only its real build/test consumers and the root tooling tasks that actually
    load it.
  - Root generation from a clean checkout still uses the current workspace
    implementation in the required order.
- Validation:
  - Query and record the root direct and transitive dependency closure before
    and after the change.
  - Add hash-selectivity tests alongside
    `ops/helpers/tests/turboInputs.test.js`.
  - Run `npm run lect:check`, all generated-data checks, root helper tests, and
    the complete shared verifier.

- Status: Pending
- Evidence status: Current shape verified; replacement design requires a
  prototype
- Evidence:
  - `ops/package-kinds.json` declares 102 TypeScript libraries.
  - `ops/lect/.lectrc.json:216` gives every library an independent
    `tsc --noEmit --project tsconfig.json` process.
  - `tsconfig.base.json:10,14` loads DOM libraries and Node ambient types for

  - The August audit measured the independent typecheck lane at 124s locally
    and found a large fixed cost from default libraries and `@types/node`.
- Problem: Cache misses pay compiler startup and shared-library parsing once per
  small package. The cost remains in every cold release because the release
  verifier intentionally disables task-cache restore.
- Recommended change:
  - Prototype both a root aggregate `--noEmit` program and a TypeScript solution

  - Keep package configuration generation in `lect`; do not hand-maintain 102
    divergent files.
  - Do not add `incremental` as a paper optimisation. It is useful in CI only if

    or a shared compiler process can consume it.
- Prerequisites: REV-001, REV-002, REV-003
- Done when:
  - The chosen lane reports the same diagnostics and checks every current
    source and type-test input.
  - A cold hosted typecheck is materially faster, with a target of at least 50%
    reduction from its measured REV-001 baseline.
  - Node-only and browser-facing packages retain the declarations they require.
- Validation:
  - Compare file inventory and diagnostics between old and candidate lanes on
    clean generated configs.
  - Run declaration builds and strict clean-consumer compilation for packages

  - Run the full root verifier and every exact Node compatibility lane.

- Status: Pending

### REV-008 — Stop release-plan merges from running duplicate verification graphs

- Status: Pending
- Evidence status: Verified duplicate orchestration
- Evidence:
  - `.github/workflows/verify.yml:6-10` runs generic CI on every push to `main`.
  - `.github/workflows/ci.yml:8-12` starts the publishing workflow on the same
    push when `.github/npm-release-plan.json` changes.
  - CI 61 and release 42 started at the same second for the same release merge.
  - Both ran the shared cold validation, five exact Node lanes, and the browser
    lane. Generic CI additionally ran Windows; release additionally ran
    examples, reproducibility, consumers, publish, and tags.
- Problem: A prepared release revision consumes two near-complete CI graphs.
  This does not directly shorten the protected publish chain, but it wastes
  runners, can increase queue contention, and repeats the most expensive cold

- Recommended change:
  - Add an explicit release-push classification rather than relying on a commit
    message heuristic.
  - On such a push, run each verification contract exactly once. Preserve or
    relocate the Windows smoke, and preserve one stable generic required status
    if branch protection expects it.
  - Let the trusted release run save main-scoped dependency and Turbo caches
    only after its cold verification succeeds; never restore those caches into
    the publish-artifact build.
  - Prefer shared reusable stages over cross-workflow trust in opaque artifacts.
- Prerequisites: REV-001, REV-002
- Done when:
  - One release merge produces one validation, one five-Node matrix, one
    browser lane, and one Windows contract check before publishing.
  - The next ordinary main or PR run can restore a trusted cache seeded by that
    release revision.
- Validation:
  - Exercise ordinary main pushes, ordinary PRs, release proposals, release
    merges, manual dispatch, and cancelled/retried release runs.
  - Confirm branch protection and npm trusted publishing still recognize the
    expected workflows.

- Evidence:
  - `.github/workflows/ci.yml:143-148`, `:177-182`, and `:213-218` use full
    history in examples, package compatibility, and browser jobs that do not
    inspect Git ancestry.
  - In sampled release jobs, those checkouts took roughly 10-35s. The slowest
    checkout is on parallel work, so the critical-path saving is smaller than
    their sum.
  - Publish and tag commands call the release script's ancestry guard, so their
    `fetch-depth: 0` cannot be removed without providing equivalent exact
    history.
  - The required `npm-production` reviewer introduced 3m01s and 14m30s gaps in
    the two successful sampled releases. That delay is not runner compute.
  - Publishing 67 packages took 3m39s inside the publish step; publishing 112
    took 6m02s. Packages are processed in dependency layers with concurrency 8
    and registry-visibility verification after publish.
- Problem: Small checkout costs remain, while release reports conflate machine
  runtime with intentional human approval. Publisher concurrency cannot be
  tuned responsibly without per-layer registry timing.
- Recommended change:
  - Use depth 1 for release examples, compatibility, and browser jobs. Keep the
    pack job's full history.
  - Keep full history for publish and tags unless an exact-base fetch is proven
    sufficient for every ancestry and tag-integrity check.
  - Add release-summary fields for validation compute, approval wait, publish
    compute, and tag compute.
  - Instrument publish layers and registry polling before testing a concurrency
    increase. Do not remove the required reviewer to improve a machine-runtime
    metric.

  - Any publisher-concurrency change is supported by repeated layer-level data

- Validation:
